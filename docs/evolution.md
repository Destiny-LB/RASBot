# 自主演进

平台以 LLM 引导的单轮候选引擎为基础，并支持有预算的长期目标：依次探索执行指令、Skill 和脚本假设，可从被拒绝的历史候选继续开发，但始终与当前采用版本做独立配对比较。它是串行的有限多候选探索，不是并行种群搜索，也不会无限自动启动下一轮。

## 入口、样本与调度

工作台“自主演进”页选择 Agent、诊断依据、2～3 个不同评测任务与预算。页面推荐最近失败任务，尽量附带同任务的成功对照；没有失败时使用最近成功任务。至少一个评测任务不在本轮诊断证据中，但不保证它从未在历史实验中出现。

推荐不调用模型、不启动实验。任务池首次从具备 prompt 的目录建立，精度 Agent 存于 `.rasbot/evaluation-pool.json`，其他 Agent 独立保存；新任务不会静默加入。每轮记录选择策略、池内容和选定任务。

服务端每 5 秒推进，关闭页面不停止轮次，重启后继续观察已有会话。启动前固定父版本、模型、任务资产、评价政策及源码摘要；固定资产发生变化会使实验失效。修改平台代码前应结束活动轮次。

RASBot 的精度 Agent 现在支持版本化执行文件包，不再只演进执行指令。

## 候选修改范围

- `openskill/01_generate_test_rules.md`：Step 1 Skill 全文。
- `scripts/*.py`：顶层 Python 执行脚本，可增加辅助脚本；暂不支持删除。
- `create_workspace.py` 和 `verify_precision_report.py` 不在修改范围；工作区创建、硬件流程、任务输入和平台验收器保持固定。
- 仍支持单独调整 `agent_instructions`，老版本和老演进记录继续可读。

## 源码版本与执行流程

1. 开始新一轮时，将旧版对应的可演进源码冻结为基线子版本。已带文件包的版本直接复用。`baseline_source` 记录开始前采用的版本；拒绝候选不会改变它。
2. 改进器同时收到执行证据、父版本指令和源文件全文。响应可以包含 `file_changes`，键为相对路径，值为修改后的完整文件内容；省略或空对象表示不改文件。仍禁止改进会话直接调用工具，代码通过结构化提案进入版本管理。
3. 平台检查路径、文件类型、大小和 Python 编译语法，将变更合并为完整 `execution_files` 快照。所有内容参与版本哈希。语法检查不代表功能正确。
4. 基线和候选分别执行任务。每个执行会话在自己的 attempt 目录创建 `execution-package`，由 `EXECUTION_ROOT` 指向；`REPO_ROOT` 提供只读任务与文档。任务契约要求使用版本化脚本，版本化 Skill 全文直接载入契约。
5. 产物仍由原始仓库中的固定验收脚本独立检查。候选修改执行侧的 `prepare_atk_submission.py` 或 `verify_trigger_coverage.py` 不会改变平台验收入口。验收前检查执行文件包和原始验收脚本是否被改写。
6. 沿用配对评测、严格晋升和回退机制；晋升后新任务使用整个候选文件包。原 PrecisionTesting 仓库不会被发布覆盖。回退采用本轮冻结并实际评测过的基线。
7. 版本观测展示 Skill、脚本的逐文件 diff；演进记录展示候选源文件。



## 决策

1. 必须完成配对；基础设施错误、人工干预或实验完整性破坏不能证明改进。
2. 候选必须通过所有生成合规性门槛。初次通过数严格优于基线时按 `generation_compliance` 晋升。
3. 双方全部通过时，每个任务候选耗时必须不超过基线的 80%。缺失、非正或非有限耗时不进入效率晋升。
4. 初次效率达标只触发复测。先候选、后基线，交换初次的执行顺序。所有任务复测仍必须全部通过，且每个配对都达到 20% 耗时降低，才能按 `generation_efficiency` 晋升。
5. 复测中基线合规性不稳定，效率结论无效；候选失败则拒绝。重复两次不等于统计显著，也不证明数值测试质量不退化。

耗时来自平台记录的试验派发时间至任务终态事件时间，包含模型、工具和验证，属于生成流程墙钟时间；不使用模型自报耗时，不使用控制器读取结果的时间。服务延迟和机器负载仍是影响因素。

## 预算和版本

仍是单父版本、单候选。2～3 个任务初测需要 4～6 次执行；按需复测后上限 8～12 次。创建轮次时为最大执行次数预分配相同会话预算，总预算仍限 30/60/120 分钟，复测不延长截止时间。对耗时较长的任务可选 120 分钟；预算不足产生无结论，不能自动晋升。

复测列表与决策持久化，可恢复执行、取消、查看轨迹、回退。工作台分开展示初次评测和效率复测，并展示晋升类别与决策原因。完整配对耗时和比值保存在 `decision.pairs`。



## 评价边界与元评价

生成门槛见 [PrecisionTesting 接入](precision-runtime.md)。报告存在且非空不等于报告语义正确；生成效率也不等于数值覆盖或故障发现能力。两次配对复测不构成统计显著性证明。

`meta_evaluation` 仅记录评价器局限及建议，不进入候选执行指令，不修改本轮规则。影子指标、结构校准及只读审计见 [评价与轨迹分析](evaluation.md)。当前没有评价器自动演进、硬件可靠性评分；长期目标支持有限串行多候选与历史分支选择。

提案使用简体中文撰写诊断、执行指令和元评价建议；JSON 键、代码、路径与命令保持原文。初始提案通过结构化 JSON 提交；随后默认开启候选开发会话，允许修改、试跑和修复，见 [候选开发](candidate-development.md)。

执行文件包是版本副本隔离，不是操作系统沙箱。脚本继承 OpenCode 执行环境权限；文件完整性不能证明某脚本被调用，需结合工具轨迹检查。权限请求不会被平台自动批准。

## 持久化、接口与恢复

- `evolution_runs` 保存协议、模型、证据、候选、试验、决策及时间线。
- `versions` 保存内容寻址版本及父子关系；`champions` 按 Agent 保存采用版本。
- 每个任务保存指令、会话轨迹、验证日志和产物摘要；版本观测展示指令及源码 diff、关联评测与当前采用状态。
- `POST /api/evolution/start` 启动，参数包含 `source_ids`、`slugs`，以及可选模型、Agent 和预算；模型必须明确。
- `GET /api/evolution` 查询，`POST /api/evolution/tick` 单步推进，`POST /api/evolution/cancel` 请求停止，POST 均使用平台请求令牌。
- `POST /api/evolution/rollback` 传入已晋升轮次 `id`；当前采用版本仍为该候选时才能回退，历史任务不改绑。

网络不确定时不重发提案；`proposal_starting` / `proposal_unknown` 需要核查会话后处理。取消保持 `cancelling` 直到确认引擎终态。预算包括准备、等待和验证；它是调度预算，本地阻塞调用与停止确认可能超过截止时间。旧记录使用原始政策，历史分数不重算。

版本由演进流程写入，手动候选表单及 `/api/candidates` 已移除。代码更新后需重启平台，新轮次才加载新能力。

## 长期目标、探索与经验

工作台“长期演进目标”复用上方选择的 Agent、诊断依据和评测任务。每个目标限制 1～12 轮，每轮 30/60/120 分钟，总截止时间为轮数乘每轮预算加一分钟调度余量。暂停不重置截止时间。预算用完不等于目标达成。

策略 `bounded-sequential-hypotheses-and-archive-v1` 轮流提示执行指令、Skill、脚本方向；这些是探索重点，不是已证明的改进假设。隔轮可以选择本目标中最近被拒绝的候选作为开发父版本 `proposal_parent`。对照 `baseline` 始终取创建实验时当前采用版本；晋升前再检查采用版本没有变化。候选内容的父子关系反映开发来源，而不是混淆成对照来源。

每个实验仍需经过独立开发验收、正式配对评测及必要的效率复测。目标不会自动把无结论当作失败改进证据：失败、取消、基础设施问题会进入 `needs_attention`，需检查后继续。连续三轮无晋升或预算用完会停止。暂停会取消当前轮并等待停止确认；继续时创建下一轮，不重放原会话。

`campaigns` 持久化目标、预算、实验关联及状态。创建实验时原子写入目标 ID 和轮次索引，目标控制器重启时先根据归属恢复，避免“实验已创建、目标记录尚未更新”造成重复创建。当前服务为单进程控制平面，不支持多个服务进程同时调度同一数据库。

`experiences` 每轮只记录一次，包含成功、拒绝和失败结果、父版本、对照版本、决策、试验 ID 与评价器。下一轮读取当前 Agent 最近六项摘要；原始正式评测任务内容不进入经验提示。经验是实验观察，不是自动推导出的通用规律；历史晋升可能已回退。评测集跨轮复用，因此不能宣称存在永久未见保留集。

- `GET /api/campaigns`：目标列表。
- `POST /api/campaigns/start`：`objective`、`agent_id`、`max_rounds`、`round_minutes`，可选 `source_ids`、`slugs`、`model`。
- `POST /api/campaigns/control`：`id` 与 `action`（pause/resume/stop）。
- `GET /api/experiences?agent_id=precision`：带证据的经验记录。

调度每个 Agent 最多一个活动轮次；不同领域可建立各自目标，但目前没有 GPU/硬件资源池，也没有并行候选执行。源码仍使用内容寻址包，不依赖 Git worktree。这使现有小型包保持兼容；扩大到完整仓库前需补充 worktree 和真正的隔离执行器。
